# Benchmarks

The current committed benchmark evidence is Ubuntu-only (x64 and arm64),
CPU-only, and generated by `.github/workflows/bench.yml` on GitHub-hosted
`ubuntu-latest` and `ubuntu-24.04-arm` runners. It is not a multi-platform
performance claim. No quantization comparison is included.

## Reproduce on Ubuntu

The workflow is the canonical reproducible path. It downloads the published f16
GGUF, builds the Release CLI, runs the script, and uploads a small, diffable
result plus provenance file. Trigger it with the GitHub CLI:

```bash
gh workflow run bench.yml --ref feat/batched-inference \
  -f variant=small -f repeats=5 -f threads=12
```

Add `-f platform=ubuntu-24.04-arm` to run the same job on the ARM64 runner
(the committed arm64 row above used `-f threads=4` to match its 4 CPUs).

The workflow supports the regular `small`, `base`, `large`, and `giant` models
and their explicitly named `small-registers`, `base-registers`,
`large-registers`, and `giant-registers` variants. `all` currently means the
four regular sizes. Register-token variants, base/large/giant sizes, and any
cross-platform or GPU measurements remain unmeasured in the committed result.
They must be run and recorded separately before being described as evidence.

For an already staged f16 GGUF on Ubuntu:

```bash
cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DDINOV2_BUILD_TESTS=OFF
cmake --build build --target dinov2-cli -j"$(nproc)"
scripts/bench.sh --models small --repeats 5 --threads 12 \
  --warmup 1 --image assets/tench.jpg --bin build/bin/dinov2-cli \
  --out benchmark_results.txt
```

`scripts/bench.sh` records the UTC timestamp, runner information, repository
SHA, exact model path and SHA-256, precision, backend, batch, image, thread
count, warmup and timed-run counts, and command inputs. It reports mean,
standard deviation, minimum, maximum, and peak RSS for each model. The timed
block is the model forward pass. A standard deviation above roughly five percent
of the mean is a reason to repeat the run on a less-loaded runner.

## Model variants

Regular and register-token checkpoints are distinct published models and must
remain distinct result rows. Register tokens are useful for dense feature and
local feature-map workflows, while regular checkpoints remain useful for exact
baseline comparisons. This document makes no quality or speed claim for an
unmeasured variant.

The benchmark scope is deliberately limited to f16 CPU inference. The repository
may load other GGUF types, but loading them is not benchmark evidence and no
quantization-specific benchmark mode or table is provided here.
